# Sparsity

How I write to you: short, plain, unmistakable. Started after a session where my replies went murky.

Questions belong in this file, not in the chat — this is the record, the chat is thrown away. Three markers:

- **A:** my answer.
- **ME:** your answer (you write these).
- **UA!** nobody has answered yet, with the reason. Count these to see what is still open.

## Why my replies went murky

1. I treated the three-bullet cap as a quota to fill, so a one-sentence answer got padded to three.
2. Two rules ask me to cite evidence and to name the other reading of your words. I met both with hedges instead of a fact, which added length and blurred the point.
3. The plain-English rule bans the true names of things but never says to use an ordinary one instead, so I coined phrases — "the pulling-out" for extracting words. ji had no lexicon to stop me.
4. I packed clauses into long sentences held together by dashes.

## Written already

1. **Strip it** — in the block at the top of `guides/pre-flight/always.md`. Fewest words that still read as grammatical American English; the limit is a cap, not a quota; adjectives only when the point fails without one.
2. **Number the bullets** — same block. Every list in a reply is numbered, so either of us can answer by number.
3. **murky** — a shorthand in `guides/pre-flight/shorthand.md`: review the chat, name the causes of the confusion, report very briefly, no fixes unless asked.
4. **A lexicon for ji** — `ji/notes/guides/pre-flight/lexicon.md`, plus a line in ji's own instructions telling me to read it at session start.

A common technical word (file, folder, pdf, browser, table) is plain English: use it, and define it once. Never invent a phrase for something already named. Only the banned list licenses a swap, and only to its listed word.

## How the two layers would work

Detail for step 4. A guide file name can exist twice: once in mono, once in the project. Today only the always file is covered, by rule 23, which says "also read" without saying what happens when the two disagree.

1. **The rule** — a name in both places is read twice: mono first, then the project's. The project adds to mono; where they disagree the project wins, and says so on the line that differs.
2. **The names that may appear twice** — always, clear writing, banned words, lexicon, pitfalls, learn, shorthand. Each project file opens with one line: "adds to mono's «name»".
3. **Making it stick** — state the rule once in the main instructions' reading list, and change the hook that injects the always file so it injects mono's first, then the project's. Otherwise the rule holds only when I remember to read.
