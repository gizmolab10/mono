## build the six lines of threading the dispatcher now, or leave them in the proposal (pac, 11 September 2026)

For: the six lines are the same under either order, kb's new work or music first, since both name this fix, so nothing is built twice. A look is 0.04 seconds over 346 files, so a fault shows on a quiet db, where the first long caller, music's scan or the ai call, would hide it under its own stall. sqlite keeps every transaction whole, so a race can fail a request and cannot spoil a row, and the whole change reverts in six lines, WAL by one pragma back. Deciding question: is a fault that a test cannot force, and that reading six lines can, enough of a proof to call the fix done, or does done wait for the first long caller, whose stall the fix exists to remove?

## once the dispatcher is threaded, a mutex around the look, or the watcher as the only thread that looks (pac, 11 September 2026)

For the mutex: three lines, a threading.Lock at the top and a with block in look and in the rules run, the standard library's, released on an exception too. The five callers keep their code and each gets a whole, current look: /all-labels answers under a file's new path the moment it is asked. RULED and the reconcile are touched by one thread at a time, so the two faults, the dict changed under an iteration and a new row inserted twice, cannot happen. No call inside the look takes the lock again, so a plain Lock does, not a reentrant one. Against the mutex: a look waits behind a look, so whatever holds the lock long, music's first scan over tens of thousands of files or an ai call of seconds per changed file inside the rules run, holds every caller of the look for as long as it runs, which is the one-request-at-a-time server again for those callers. So the mutex comes with a rule: the lock is held for a look of a fraction of a second, and long work, a scan or an ai call, runs in a thread of its own outside it, writing rows through its own connection, which sqlite's 5 second wait already handles. That is the kb list's other half, long work in a thread that answers progress. For the watcher alone: no lock at all, since one thread touches RULED and reconciles, and a request never blocks on a look. Against: /all-labels answers what the last pass left, up to 3 seconds stale, so a file moved a moment ago answers under its old path once. /rescan and a rule added or removed ask the watcher for a pass and wait for it, an Event and a flag, ten lines, not three, and the test suite's in-process calls of the look go through the watcher too. Deciding question: does a caller need its own look the moment it asks, the mutex, or a look within 3 seconds, the watcher alone, given that either way the long work runs outside the look?

## proposal: code debt belongs in the zone, like ideas (28 August 2026)

An owed item is an idea that has been accepted but not yet done. The zone already holds ideas — things captured without being believed — and the debt list is the same kind of thing at a later point on the same arc: accepted, waiting, not yet true of the code. So it stays in `zone/`, beside `ideas.md`, and never becomes a truth. Truth files say what the code IS; a debt list says what it is not.

That is what the move on 27 August already did, by hand. This proposal is for making it the design rather than an accident.

**What follows from it**

- **`zone/debt.md` is the one place work is owed.** One file per project. Nothing new is ever written to the old `memory/<project>/notes/work/` files.
- **The done section stops growing.** A finished item is deleted, and a `D:` line in the log says what was done. Git holds the corpse; the log holds the recent; the debt list holds only what is still owed. The 292 finished checkboxes now in the file are history that came along with the move — they can be cut at the next settle without losing anything.
- **Settle triages debt the way it triages ideas.** Ideas get promote, keep, or cull. Debt gets: done (delete it, log a `D:`), still owed (leave it), or dead (delete it, log why). Three settles untouched is the same signal it is for an idea — do it or drop it.
- **An idea promoted becomes debt, not truth.** That is the missing step in the arc: `propose` puts a thing in `ideas.md`; deciding to build it moves the line to `debt.md`; building it writes the truth and deletes the debt line. Today `propose` has nowhere to hand a thing off to.
- **handoff is not a second file.** Where to pick up is the first unchecked item in `debt.md`, plus the current-state paragraph in `index.md` and the log's `Q:` lines. The file that moved can be read and emptied at the next settle rather than kept.

**Cost.** One more file in every project's zone, and a settle step that touches it. Both small.

**Open question:** does `soon` stay as a heading inside `debt.md`, or does a debt line carry a tag — `now`, `soon`, `tabled` — the way a file does?
