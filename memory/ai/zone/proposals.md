# Proposals

## build the six lines of threading the dispatcher now, or leave them in the proposal (pac, 11 September 2026)

For: the six lines are the same under either order, kb's new work or music first, since both name this fix, so nothing is built twice. A look is 0.04 seconds over 346 files, so a fault shows on a quiet db, where the first long caller, music's scan or the ai call, would hide it under its own stall. sqlite keeps every transaction whole, so a race can fail a request and cannot spoil a row, and the whole change reverts in six lines, WAL by one pragma back. The hooks open the db through database.py as the same user, so WAL changes nothing for them. Against: nothing today asks for it, principle 3, and this is the third pac saying so. The proof is weak: the new check fires two rescans at once, and at 0.04 seconds each they seldom overlap, so a pass says no error was seen, not that the wait was exercised, and a race that a test cannot force is proved only by reading the six lines. WAL puts two files beside the db, so every future saved file made from ov.db, step 2's first, must checkpoint or lose the last writes, a rule for a plan not yet built. And the live dispatcher is the one ov and the hub use, so a slip stalls or fails ov's fetches until a restart, **risk low**, since the db is safe and the revert is six lines. Deciding question: is a fault that a test cannot force, and that reading six lines can, enough of a proof to call the fix done, or does done wait for the first long caller, whose stall the fix exists to remove?

## once the dispatcher is threaded, a mutex around the look, or the watcher as the only thread that looks (pac, 11 September 2026)

For the mutex: three lines, a threading.Lock at the top and a with block in look and in the rules run, the standard library's, released on an exception too. The five callers keep their code and each gets a whole, current look: /all-labels answers under a file's new path the moment it is asked. RULED and the reconcile are touched by one thread at a time, so the two faults, the dict changed under an iteration and a new row inserted twice, cannot happen. No call inside the look takes the lock again, so a plain Lock does, not a reentrant one. Against the mutex: a look waits behind a look, so whatever holds the lock long, music's first scan over tens of thousands of files or an ai call of seconds per changed file inside the rules run, holds every caller of the look for as long as it runs, which is the one-request-at-a-time server again for those callers. So the mutex comes with a rule: the lock is held for a look of a fraction of a second, and long work, a scan or an ai call, runs in a thread of its own outside it, writing rows through its own connection, which sqlite's 5 second wait already handles. That is the kb list's other half, long work in a thread that answers progress. For the watcher alone: no lock at all, since one thread touches RULED and reconciles, and a request never blocks on a look. Against: /all-labels answers what the last pass left, up to 3 seconds stale, so a file moved a moment ago answers under its old path once. /rescan and a rule added or removed ask the watcher for a pass and wait for it, an Event and a flag, ten lines, not three, and the test suite's in-process calls of the look go through the watcher too. Deciding question: does a caller need its own look the moment it asks, the mutex, or a look within 3 seconds, the watcher alone, given that either way the long work runs outside the look?

## thread the dispatcher now, ThreadingHTTPServer in place of HTTPServer, or with kb, as the performance fix under the kb list (pac, 11 September 2026)

For: the change is the server's base class on one line and its import, the standard library's own, its request threads daemon so a restart's exit is not held. The db is opened per call, every write sits inside one transaction, and sqlite waits up to 5 seconds for a lock, so the watcher thread already runs beside the server on the same db, and the hub's long routes, rebuild, restart sites and tests, already run in threads of their own. A look takes 0.04 seconds today over 346 files, so the fix is proved on a quiet db before music's tens of thousands make a look long. Against: a look has five callers, the watcher every 3 seconds, /all-labels before it answers, /rescan, and a rule added or removed rerunning everything, and RULED, a plain dict, is read and written by every rules run, so two looks at once can raise dictionary changed size during iteration, and two reconciles at once can insert the same new row twice, the second failing on UNIQUE. So the fix is a lock around the look and the rules run as well, three lines, principle 2's minimum being more than one. The suite starts a plain HTTPServer of its own, so a threading fault shows only once the test starts the threaded one and fires two looks at once. And nothing today asks for it: 0.04 seconds stalls nobody, so under principle 3 the stall the ai call would bring is the ai's cost, not the dispatcher's. Deciding question: is the lock around the look worth writing before anything holds the server longer than 0.04 seconds, or with the first thing that does, the ai call or music's scan?

## the proposed rules: the ai as a third writer of labels, instructed by a markdown file beside each plugin and run inside the rules pass, or no ai writer, the composing and the pattern rules alone (pac, 11 September 2026)

For: the db already keeps ai among who wrote this, ov already passes over ai rows until one is accepted, the rules pass already runs on changed files alone, and ji already makes the chat call, so the new code is the instructions file's read, one call, the settings file and the editor's accepting, principle 2's minimum. A rule never changes or removes a label a person put on, and the proposal keeps that: no hand row and no rule row is touched. The composing reads a bare file's first heading and first sentence and gives a fallback kind, where the ai reads the whole text, so a bare file gets a better first answer. Off, it costs nothing. Against: today the db holds 346 files, 13 with no kind and 0 ai rows, so the bare case is 13 files, and the composing already answers it the first time each is opened, which makes the third writer speculative under principle 2 until a count says otherwise. The dispatcher answers one request at a time, so every call, seconds each, stalls the hub and ov, the hooks reading the db file and not the server, until the threading fix under the kb list is built. The base url, the key and the workspace name would live in two places, ji's preferences and the dispatcher's settings file, two files claiming one topic. The lexicon has no entry for the ai as a writer, and the word collides with ai the host, so every sentence about the ai in the ai host reads two ways. And music gets nothing until a song takes tags, so the common mechanism is built for one specialty and meant for two, strip step 3's medium risk again. Deciding question: are 13 bare files of 346, each composed the first time it is opened, worth one call per changed file and a second meaning for ai now, or after kb exists and the threading fix is in?
