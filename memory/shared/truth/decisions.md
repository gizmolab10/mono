- 10 September 2026 — **call the new truth creating a library.** What exists: the rule decided today, four sentences on how a library is used — nothing built on its own, one alias per library per host in two files, one bridge per library per host, and a library that imports a library does the same — has no home. Its sibling-to-be is `create a project.md`, an imperative. The two truths nearest it are gerunds, core's `adopting core.md` and the zone's `incorporating a project.md`. The name offered first was `libraries.md`. For creating a library: it pairs with create a project, one for a project and one for a library, so a reader making one knows which to open, and a library is made only once while it is used many times, so the making is the rarer and easier-to-forget act. The file then also carries what a library must be, which the four sentences do not say: its own tsconfig and vitest config so it checks alone, no host vocabulary, state in the host, and its own bridge to any library it uses — the lessons adopting core.md paid for. Against: three of the four sentences are the host's side, taking a library on, and a host reading how to take one would not open a file called creating. The sibling is an imperative and this is a gerund; match one and mismatch the other. `libraries.md` says the subject and neither side. Middle path: `create a library.md`, imperative like its sibling, in two sections, what a library is and how a host takes one on, with create a project.md pointing at the second as a step. Cost, counted: one file of about twenty lines, one line in create a project.md, one line in adopting core.md saying it is core's case of the rule, and one lexicon entry, library, which the undecided library-term pac has waited on since 8 September. Deciding question: is the file about making a library or about using one — and does the name follow its sibling's form, create, or its neighbors', adopting and incorporating? Decided 10 September 2026: `libraries.md`, the subject and neither side, in two sections, what a library is and how a host takes one on. Moved to the zone the same day.

- 10 September 2026 — **libraries resolve through the workspace, not through aliases.** What exists: every host reaches a library through an alias written in three places that must agree, tsconfig's paths, vite's resolve, and a standalone vitest config where a host keeps one; adopting core.md calls this the wiring, and names the lesson paid for it, that a test runner reading a vitest config of its own needs the alias a third time. Seven tsconfigs carry the core alias and two the gallery alias. panel's and gallery's own files reach core the same way, through the alias of whatever host is building them, and through their own when checked alone. yarn has already linked core, panel and gallery into the root node_modules, since the root package.json names them as workspaces, and nothing reads those links. No library has an `exports` field, and every tsconfig allows an import to name its `.ts` extension. Nothing is published outside mono; lv and mj are built by vite from the whole checkout on Netlify. The proposal in zone/proposals.md: an `exports` map in each library's package.json, pointing at its source, in place of every alias. For: one map per library in place of three lines per host per library, and the lines that must agree are gone with them. A library's files resolve core on their own, from any host or none. It is the way TypeScript, vite and vitest already read a package, so no config of ours teaches any of the three anything. The bridges and the alias tests stay as they are: the specifiers do not change shape. Against: an `exports` pattern adds no extension, so either the map carries one pattern per kind of file, `.ts`, `.svelte` and `.css`, and a file named `.svelte.ts` is caught by the wrong pattern and fails to resolve, or every bridge line names its file's extension outright, which is 110 lines today across eight bridges. The alias is a plain prefix swap and has no such edge. And the links the map relies on are made by yarn's install at the root; whether Netlify installs at the root when the base directory is a host is unproved, and lv's and mj's builds work today without any link. Middle path: one pattern only, `"./*": "./src/lib/*"` for core and `"./*": "./src/*"` for gallery and panel, and every bridge line names its extension, `.ts`, `.svelte`, `.svelte.ts` or `.css`. One rule, no edge, and the map is a single line. Cost, counted: three maps of one line; 110 bridge lines each gaining an extension; the alias lines out of seven tsconfigs, seven vite configs and two vitest configs; the wiring section of adopting core.md and lv's structure.md rewritten; one deploy each of lv and mj to prove the link on Netlify, before the aliases go. Deciding question: is three agreeing lines per host per library a cost worth 110 extensions and an unproved Netlify link — and if Netlify's install does not make the link, does the deploy fail loudly enough to be caught before the aliases are removed? Decided 10 September 2026: dead. The aliases and the bridges stay, and a library that imports a library does the same.
