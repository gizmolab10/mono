# Decisions

## Decisions made during 2026

- 30 August 2026; **one pile at mono's root** — what matters is one pile, not where it sits. Core declares only what its code uses (color2k, rbush for the hits manager, the svelte toolchain), joins the workspaces, and the root hoists; the svelte nohoist went on 30 August 2026.

## Evaluations (pac) made during 2026

- 1 September 2026; **move Hamburger into core.**
  What exists: two hosts draw a hamburger, and both already take the drawing from core — `svg_paths.hamburger(size)`, which core has owned since the carve. ov's sits inside `Controls.svelte` as a button in the top row; lv's is `Hamburger.svelte`, a button of its own placed over the top-left corner. Neither is on screen for lv today, its markup commented out.
  For: the same button twice is the duplication this whole adoption removes, and the pattern is settled — a component that takes the host's state as a prop and hands the press back, exactly as Big_Pill and Status_Line now do. Core already carries the drawing, the size (`k.size.big`, commented "the hamburger") and the padding (`k.pad.hamburger`), so everything the button is made of is core's already; only the markup around it is not. A second host asking for a hamburger is the evidence a library is what it is for.
  Against: what differs is not the button, it is where it stands. ov's is a flex child in a row, transparent, on the accent, colored by `--text-on-accent` with the cursor stamp painting the path. lv's is fixed over the corner with a white fill, its own border, a corner radius and a stacking layer, three rem square. A component that must be both takes a prop for every one of those, which is the prop soup the composition guide names — and the part they truly share is one line, `svg_paths.hamburger(size)`, which both already call. Moving the markup moves 20 lines to save 6.
  A middle path: leave the button in each host and let core own only what it already owns — the path, the size, the padding. That is the state today, so the honest question is whether anything is actually duplicated.
  The cost, counted: a core component with props for the fill, the border, the radius, the layer and the placement, plus edits at both call sites and two blocks of styling to reconcile. The middle path costs nothing.
  Deciding question: is the hamburger one component with two blocks of styling, or two buttons that happen to draw the same path — and does placement belong to a library at all, when the host owns the layout that decides it? The two blocks differ on all seven counts: background (transparent against white), border (none against a `--thick` white one), corner (`--radius-tiny` against `0.25rem`), placement (in the flow, nudged 4px left, against fixed `0.5rem` from top and left), size (none given against `3rem` square), stacking layer (none against 10), and how the path is colored (`--text-on-accent` painted `--hover` under the cursor, against `currentColor` going lightgrey).
  Decided 1 September 2026: the component moves into core; only the two blocks of styling remain within their host. core owns the button — its markup, the drawn path, the size — and takes the press back as a prop, the same treatment as Big_Pill and Status_Line. Each host keeps its own look, reaching the button by the class it wears. lv's class is renamed `hamburger-button`, matching ov's, so one block of styling answers for both.

- 31 August 2026; **the stylesheet's door: a bare import in Core.ts, or main.ts keeping its own.**
  The situation: ov adopted core's `main.css` and imports it at `main.ts` line 9 as `import 'core/main.css'`. That makes two files in ov reaching through the alias, against the rule at the top of this adoption — "only Core.ts reaches through the alias."
  For moving it into Core.ts: one door, exactly as written, and the precedent is already there — `Extensions` rides Core.ts as a bare `import 'core/ts/common/Extensions'`, and the lesson from that crash says a side-effect module is taken that way. A rule with one silent exception is a rule nobody can check; a rule with none can be proved by grep, which is how this was found.
  Against moving it: a stylesheet is not a module a host consumes, it is a resource the page loads, and Core.ts is imported by nearly every file in ov — so the styles would arrive with whichever file happens to be pulled in first, wherever that is. Today they arrive at one named moment, last in `main.ts`, after the app, the managers and svelte's mount. Cascade order decides which rule wins where two match equally, so moving the load point can change what is drawn without changing a single style. And the rule's own reason was type safety and one place to look for adoptions — neither of which a stylesheet has.
  A middle path: keep the import in `main.ts` and reword the rule to say only Core.ts reaches through the alias *for code*, naming the stylesheet as the one resource that does not pass through it.
  The cost, counted: moving it is one line deleted from `main.ts` and one added to `Core.ts`, with a real chance of a visual change that only Jonathan's eyes can catch. The middle path is one sentence in `adopting core.md` and no code touched.
  Deciding question: is the one-door rule about where the alias may be named, or about where adoptions are listed — and does a stylesheet, which has no exports and whose load order is visible on screen, count as an adoption at all?
  Decided 31 August 2026: the stylesheet keeps its own door. The rule now reads "for code, only Core.ts reaches through the alias", and names `main.ts` as the one other place, for `main.css` alone. Two doors, both written down.
  On the claim that a rule with one silent exception cannot be checked: the risk is that a second exception arrives and nothing notices. Whoever adds it reads a rule with an exception already in it, so the shape is established, and the same grep that found this one — every `'core/` in the host's source — now returns a hit that is meant to be there and cannot say whether the others are. The check that closes it is a test in ov: gather every `'core/` in `src/`, expect exactly two files, and expect `main.ts`'s only one to be `core/main.css`. It fails the day a third door opens, and it is a plain search over text, so it needs no page and no app.

- 31 August 2026; **core's BuildNotes: hand the build-notes text in as a prop from the host.**
  The fault first: `BuildNotes.svelte` line 5 reads `import buildsRaw from '../../md/builds.md?raw'`, and `find core/src -name "*.md"` returns nothing. The path is relative to core, so adopting the component would point ov's build at a file that is not there. Core's own check passes only because the `vite-env` declaration says what the `?raw` suffix yields without asking whether the file exists.
  For the prop: it is the same boundary just drawn for Big_Pill and already drawn for Status_Line — the host owns its content, core draws it. A build-notes table is the host's own history; a second host would have its own, and no library should name a file inside a project it has never heard of. The component already takes `onclose` as a prop, so the treatment is the one it half has. And ov already reads that file in a second place — `App.svelte` line 14 imports the same `?raw` for the build number — so ov holds the text whether or not the component asks for it.
  Against the prop: two call sites in one file now pass a value neither needed before, and the text is a constant that never changes while the app runs, so a prop threads a fixed thing through a boundary for its own sake. A host that forgets to pass it gets an empty table with no complaint. The alternative reading is that a library may name a well-known path by convention — the way it already names `logs/` through Debug — and then core keeps its own `md/builds.md` and the import stands.
  The cost, counted: one prop added to core's component, one line deleted from it, and one attribute at `App.svelte` line 167. ov's own copy at `svelte/main/BuildNotes.svelte` then goes.
  Deciding question: is a file path a library may assume, or is every path the host's to supply — and if core may assume `logs/` through Debug, why not `md/builds.md` here?
  Decided 31 August 2026: every path is the host's to supply. The text arrives as a `table` prop, and the "threads a fixed thing for its own sake" objection was wrong — Jonathan pointed out that App already holds that text for the build number, so the prop hands over a value in hand and leaves ov with one reader of the file where there were two. The prop is read through `untrack`. Svelte watches every prop for changes and warns when one is read once at setup; `untrack` is how the code tells the Svelte compiler that reading it once is meant. The text never changes while the popup is open, and the three paging values that start from it are changed by the paging itself, so making them follow the prop would break them.

- 31 August 2026; **core's Big_Pill: move `Tag_Areas.ts` into core, or make the component take what it needs as props.**
  The fault first: core's own check ran for the first time on 31 August 2026 and found that `Big_Pill.svelte` imports `Tag_Area`, `area_reads` and `tags_shown` from core's types barrel, which has never held them — they live in `ov/src/lib/ts/types/Tag_Areas.ts`. Five errors, one cause. The component has never compiled inside core, so the adoption plan's line saying ov should adopt it forward rests on a file that does not build.
  For moving the file: `Big_Pill` compiles at once, with no signature change and no edits at ov's two call sites. The three things it wants are honest library material — `Tag_Area` is a name and a list of words, and `tags_shown` and `area_reads` are pure: each takes an area and two lists and returns a list or a string, touching no store, no manager and nothing on screen.
  Against moving the file: the same file also holds `TAG_AREAS` — ov's ten named areas and its thirty-five tags — and `area_of` and `tags_without_area`, which read ov's closed tag list. That is the host's own vocabulary, and core's principle is that state lives in the host. A second host would inherit ov's words. Moving only the three means splitting one file in two, and two files named for one topic is the duplication bug.
  For the props: core stops naming the host's vocabulary at all. The component already takes `opened` and `ontoggle_area` as props for exactly this reason, so this is the treatment already chosen for this file, applied to the rest of it. What is handed in is two derived values the host already computes.
  Against the props: it is a signature change, so core's component and ov's two call sites change in one act, and every later host pays the same price. And a structural type still crosses the boundary — whatever `area` is, it has a name and a list of tags, so core knows that much of the host's data whether or not a type says so.
  The cost, counted: moving the file is one relocation and one barrel line. The props are a rewrite of the component's props block and edits at `Browse_Filters.svelte` line 348 and `Editor_Filters.svelte` line 523.
  Deciding question: is a pure function over a host's data library material, or does core stay clean only by knowing nothing about that data at all — not even the two functions that never touch a store?
  Decided 31 August 2026: keep core clean. Big_Pill takes what it needs as props; `Tag_Areas.ts` remains ov's.

- 30 August 2026; **only core has node modules — ov's moves there.**
  For: one copy of svelte, vite and typescript instead of a 16M pile per project; version skew between core and its hosts becomes impossible; core is what every host shares, so core holding the shared dependencies reads naturally; installs and disk both shrink.
  Against: node's resolver only walks *up* — ov cannot see a sibling's node_modules, so every tool (vite, tsc, vitest, the svelte plugin) would need aliases or symlinks, fighting the platform forever. And the wish already has a granted form: mono is a yarn workspace, whose whole job is hoisting shared dependencies to ONE pile at the root — 1,221 packages sit there now, and ov's own 16M exists only because of the deliberate `nohoist` for svelte. Moving the pile to core also inverts ownership: hosts would inherit core's lockfile choices even for host-only dependencies like markdown-it.
  A middle path: core declares the dependencies its code needs, ov depends on core, and the workspace hoists both to the root — "only core" becomes "only the root", which the machinery already supports; the open question is whether the svelte nohoist can go.
  Deciding question: is the wish one pile anywhere (the root already does it), or literally the pile living in core (which node's resolution fights everywhere)?
