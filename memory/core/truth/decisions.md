# Decisions

## Decisions made during 2026

- 30 August 2026; **one pile at mono's root** — what matters is one pile, not where it sits. Core declares only what its code uses (color2k, rbush for the hits manager, the svelte toolchain), joins the workspaces, and the root hoists; the svelte nohoist went on 30 August 2026.

## Evaluations (pac) made during 2026

- 9 September 2026 — **move mj's four preference keys into core.** What exists: mj's `managers/Preferences.ts` names four keys, `show_details`, `preferences_open`, `color_accent` and `color_background`, over one instance of core's `Preferences` under `mj.`. ov's names thirty-four, and three of mj's four are among them letter for letter: `show_details`, `color_accent`, `color_background`. The fourth differs in shape: ov saves `details_open`, a list of the open sections' names, where mj saves one yes or no for its one section. gallery's Persistence names five of its own, none of these. core's truth, adopting core.md, says state lives in the host and behavior in core, and that core holds no remembered value, only the way to read and write one under a host's prefix. The pac above it, decided this morning, put the keys in each host. A proposal to name the universal keys once in core was dropped by Jonathan the same day, before anything was built. For: three names already exist twice, letter for letter, and mu, drawing panel too, would write them a third time. What a host remembers about panel's three regions — the column shown, a section open, the two colors — is the same fact in every host that draws them, and core's Colors owns the two color stores already. One enum in core, and each host's enum holds only what is its own. Against: a key's name is the name of a piece of state, and core's rule keeps state in the host; an enum of keys would be the first host-shaped thing in core. `preferences_open` names a section only ov and mj have, so it is host vocabulary, which core keeps none of. ov and mj do not agree on the fourth key's shape, so one enum can hold both names but cannot make them one fact. And the decision this morning and the dropped proposal both said keys stay in the host; this reopens both. Two middle paths. One: the enum goes to panel, not core — the three regions are panel's, so what a host remembers about them is panel's vocabulary, and a host takes panel's keys as it takes panel's files; core keeps no key. Today that means a fourth version of the same lines, since no host imports panel. Two: the two colors alone move to core, since core's Colors holds their stores and pushes them onto the page, and the two layout keys stay in the host. Cost, counted: one enum of four names, about ten lines, in core or in panel; four lines out of mj's enum and three out of ov's, each reading the library's instead, or ov keeps its own and the two drift; one line in each Core.ts; the stored names stay as they are, so nothing a viewer chose is lost. Deciding question: is a key's name behavior, which is core's, or state, which is the host's — and if a name may live in a library at all, is that library core, whose rule forbids host vocabulary, or panel, whose regions the names describe?

- 9 September 2026 — **move Persistence into core.** What exists: two hosts remember things across a reload, each with its own code. ov has `Preferences.ts`, a class with read, write, remove, clear and a store that saves itself, every key prefixed `ov_`, plus an enum naming its thirty-odd keys. gallery and lv have `Persistence.ts`, two functions that read and write a flag in local storage plus one named pair per thing remembered, every key prefixed `gallery.`, with a test beside each. mu, mj and panel remember nothing yet. core's own truth says core holds no state and no preferences, and adopting core.md says the host pays at startup by reading its remembered values into core's stores. For: reading and writing local storage is behavior, and behavior is core's. Two hosts already do it in two ways, which is the duplication the adoption exists to end, and the third host to remember something would write a third. The keys and the prefix are the state, and they stay with each host, as ov's enum does. One class in core taking the prefix, and each host's file shrinks to its enum and one line making the instance. Against: core's truth says no preferences, in those words, and a file in core named for remembering reads as state whatever it holds. The two mechanisms differ — ov's stores any value as json, gallery's stores flags — so one of the two hosts changes what it saves, or the core class carries both shapes. And gallery's Persistence is already sorted by the proposal in gallery's zone, mechanism to gallery's library and keys to the host, which this pac would undo one level up. A middle path: core takes the mechanism as a class with a prefix, the hosts keep their keys and their named wrappers, and the truth's sentence is rewritten to say core holds no remembered values, only the way to read and write one. Cost, counted: one core file of about fifty lines and one test, one line in each host's Core.ts, ov's file cut to its enum and one instance, gallery's and lv's Persistence cut to their named pairs over core's functions, and their two tests re-pointed. Deciding question: is reading and writing local storage behavior, which is core's, or state, which is the host's — and if core's, does the truth's no preferences stay as written? Decided 9 September 2026: the middle path. core's `utilities/Preferences.ts` is the class with a prefix, the hosts keep their keys, and adopting core.md says no remembered values in place of no preferences. Later the same day lv began importing gallery, so gallery's Persistence holds the keys for both and lv hands it the prefix.

- 7 September 2026; **add bare-bones versions of ov's sidebar, controls top row and operation view to core.** What exists: ov's `App.svelte` places three components inside its frame — `Controls` across the top (489 lines), `Details` down the left (173), `Operation` filling the rest (53) — and keeps the frame's own arithmetic for itself: whether both regions fit (`width - gap * 3 >= k.width.small + k.width.big`), the details-only fallback, and each region's width, all from core's own numbers, since `k.width.small` is commented "the details column" and `k.width.big` "the smallest useful width for the region beside details". Strip each of the three to what is not host state, host vocabulary or host look, and this is what is left. Operation: a div of a given width whose contents switch on `w_operation` among `Report`, `Edit` and `Browse` — the switch is ov's `T_Operation`, the three are ov's components, so the bone is a div with a width and a slot. Details: a div of a given width holding a `Stack` of sections and a foot `Separator` — both already core's — filled by `D_Preferences` and `D_Repair`, which are ov's; the bone is a div with a width around a Stack the host fills. Controls: a flex row holding a `Hamburger` at the left, then either the editing tools (back, steppers, ancestry, a name input, new/obsidian/send/delete with a delete-confirmation) or a spacer and two build buttons — every one of those reaching `Operations`, `Saving`, `Files` and `T_Bundle`; the bone is a row with the Hamburger and a slot. For: a second host is coming that wants exactly this shape — mu's goal reads "ov's structure, with tags and kinds swapped for metadata" — and the three regions are the structure; the layout numbers are core's already, so a component reading them is more honest than a host writing the arithmetic out again; the pattern is settled three times over — Hamburger, Big_Pill, Status_Line each take state as props and hand acts back — and each bone above fits it. Against: no host but ov draws any of the three today — mj's and mu's `App.svelte` are one line each, lv's svelte folder names none of them — so the Hamburger pac's own test, "a second host asking is the evidence a library is what it is for", is not met yet; each bone, stripped, is a div with a width and a slot, ten lines, and a library component that is a slot costs a call site, a props block and a block of host styling for what a host writes in one line; the thing that is actually shared, the frame arithmetic, sits in `App.svelte` and is named by none of the three; and the Hamburger decision left every block of styling in the host, so three more components would each come with three more `:global` blocks to reconcile. Middle paths, two: (1) cut one component instead — the controls row, the two boxes and the status line as snippet slots, the hamburger and the width arithmetic inside it, `details_shown` as a prop and the press handed back — so what moves is the logic App.svelte holds, and Controls, Details and Operation stay ov's fillings; (2) wait for mu to draw its first sidebar, and cut then, with two hosts to read the bone from rather than one. Cost, counted: the three bones are three new files under `svelte/support`, three edits at ov's `App.svelte` call sites, and three blocks of styling moved or wrapped; the Frame is one file of roughly the sixty lines of arithmetic and markup App.svelte holds, and App.svelte shrinks by the same; waiting costs nothing today and one read of mu's version later. Deciding question: once state, vocabulary and look are stripped, is a div with a width and a slot worth a library component at all — or is the shareable thing the frame arithmetic none of the three names, which argues for one component rather than three bones — and does the cut wait for mu's first sidebar, when the Hamburger test would be met? Later the same day: mu and mj took panel whole, each as its own files, so three hosts draw the three regions and the test is met. Waiting is no longer a middle path. What remains to decide is three bones or one component, with three versions of the same 200 lines now in the repo to read the bone from. Decided 7 September 2026: no. panel imports core, not the other way, and nothing of panel moves into core. The bare bones live in panel, and a host takes them from there.

- 1 September 2026; **move Hamburger into core.** What exists: two hosts draw a hamburger, and both already take the drawing from core — `svg_paths.hamburger(size)`, which core has owned since the carve. ov's sits inside `Controls.svelte` as a button in the top row; lv's is `Hamburger.svelte`, a button of its own placed over the top-left corner. Neither is on screen for lv today, its markup commented out. For: the same button twice is the duplication this whole adoption removes, and the pattern is settled — a component that takes the host's state as a prop and hands the press back, exactly as Big_Pill and Status_Line now do. Core already carries the drawing, the size (`k.size.big`, commented "the hamburger") and the padding (`k.pad.hamburger`), so everything the button is made of is core's already; only the markup around it is not. A second host asking for a hamburger is the evidence a library is what it is for. Against: what differs is not the button, it is where it stands. ov's is a flex child in a row, transparent, on the accent, colored by `--text-on-accent` with the cursor stamp painting the path. lv's is fixed over the corner with a white fill, its own border, a corner radius and a stacking layer, three rem square. A component that must be both takes a prop for every one of those, which is the prop soup the composition guide names — and the part they truly share is one line, `svg_paths.hamburger(size)`, which both already call. Moving the markup moves 20 lines to save 6. A middle path: leave the button in each host and let core own only what it already owns — the path, the size, the padding. That is the state today, so the honest question is whether anything is actually duplicated. The cost, counted: a core component with props for the fill, the border, the radius, the layer and the placement, plus edits at both call sites and two blocks of styling to reconcile. The middle path costs nothing. Deciding question: is the hamburger one component with two blocks of styling, or two buttons that happen to draw the same path — and does placement belong to a library at all, when the host owns the layout that decides it? The two blocks differ on all seven counts: background (transparent against white), border (none against a `--thick` white one), corner (`--radius-tiny` against `0.25rem`), placement (in the flow, nudged 4px left, against fixed `0.5rem` from top and left), size (none given against `3rem` square), stacking layer (none against 10), and how the path is colored (`--text-on-accent` painted `--hover` under the cursor, against `currentColor` going lightgrey). Decided 1 September 2026: the component moves into core; only the two blocks of styling remain within their host. core owns the button — its markup, the drawn path, the size — and takes the press back as a prop, the same treatment as Big_Pill and Status_Line. Each host keeps its own look, reaching the button by the class it wears. lv's class is renamed `hamburger-button`, matching ov's, so one block of styling answers for both.

- 31 August 2026; **the stylesheet's bridge: a bare import in Core.ts, or main.ts keeping its own.** The situation: ov adopted core's `main.css` and imports it at `main.ts` line 9 as `import 'core/main.css'`. That makes two files in ov reaching through the alias, against the rule at the top of this adoption — "only Core.ts reaches through the alias." For moving it into Core.ts: one bridge, exactly as written, and the precedent is already there — `Extensions` rides Core.ts as a bare `import 'core/ts/common/Extensions'`, and the lesson from that crash says a side-effect module is taken that way. A rule with one silent exception is a rule nobody can check; a rule with none can be proved by grep, which is how this was found. Against moving it: a stylesheet is not a module a host consumes, it is a resource the page loads, and Core.ts is imported by nearly every file in ov — so the styles would arrive with whichever file happens to be pulled in first, wherever that is. Today they arrive at one named moment, last in `main.ts`, after the app, the managers and svelte's mount. Cascade order decides which rule wins where two match equally, so moving the load point can change what is drawn without changing a single style. And the rule's own reason was type safety and one place to look for adoptions — neither of which a stylesheet has. A middle path: keep the import in `main.ts` and reword the rule to say only Core.ts reaches through the alias *for code*, naming the stylesheet as the one resource that does not pass through it. The cost, counted: moving it is one line deleted from `main.ts` and one added to `Core.ts`, with a real chance of a visual change that only Jonathan's eyes can catch. The middle path is one sentence in `adopting core.md` and no code touched. Deciding question: is the one-bridge rule about where the alias may be named, or about where adoptions are listed — and does a stylesheet, which has no exports and whose load order is visible on screen, count as an adoption at all? Decided 31 August 2026: the stylesheet keeps its own bridge. The rule now reads "for code, only Core.ts reaches through the alias", and names `main.ts` as the one other place, for `main.css` alone. Two bridges, both written down. On the claim that a rule with one silent exception cannot be checked: the risk is that a second exception arrives and nothing notices. Whoever adds it reads a rule with an exception already in it, so the structure is established, and the same grep that found this one — every `'core/` in the host's source — now returns a hit that is meant to be there and cannot say whether the others are. The check that closes it is a test in ov: gather every `'core/` in `src/`, expect exactly two files, and expect `main.ts`'s only one to be `core/main.css`. It fails the day a third bridge is built, and it is a plain search over text, so it needs no page and no app.

- 31 August 2026; **core's BuildNotes: hand the build-notes text in as a prop from the host.** The fault first: `BuildNotes.svelte` line 5 reads `import buildsRaw from '../../md/builds.md?raw'`, and `find core/src -name "*.md"` returns nothing. The path is relative to core, so adopting the component would point ov's build at a file that is not there. Core's own check passes only because the `vite-env` declaration says what the `?raw` suffix yields without asking whether the file exists. For the prop: it is the same boundary just drawn for Big_Pill and already drawn for Status_Line — the host owns its content, core draws it. A build-notes table is the host's own history; a second host would have its own, and no library should name a file inside a project it has never heard of. The component already takes `onclose` as a prop, so the treatment is the one it half has. And ov already reads that file in a second place — `App.svelte` line 14 imports the same `?raw` for the build number — so ov holds the text whether or not the component asks for it. Against the prop: two call sites in one file now pass a value neither needed before, and the text is a constant that never changes while the app runs, so a prop threads a fixed thing through a boundary for its own sake. A host that forgets to pass it gets an empty table with no complaint. The alternative reading is that a library may name a well-known path by convention — the way it already names `logs/` through Debug — and then core keeps its own `md/builds.md` and the import stands. The cost, counted: one prop added to core's component, one line deleted from it, and one attribute at `App.svelte` line 167. ov's own copy at `svelte/main/BuildNotes.svelte` then goes. Deciding question: is a file path a library may assume, or is every path the host's to supply — and if core may assume `logs/` through Debug, why not `md/builds.md` here? Decided 31 August 2026: every path is the host's to supply. The text arrives as a `table` prop, and the "threads a fixed thing for its own sake" objection was wrong — Jonathan pointed out that App already holds that text for the build number, so the prop hands over a value in hand and leaves ov with one reader of the file where there were two. The prop is read through `untrack`. Svelte watches every prop for changes and warns when one is read once at setup; `untrack` is how the code tells the Svelte compiler that reading it once is meant. The text never changes while the popup is open, and the three paging values that start from it are changed by the paging itself, so making them follow the prop would break them.

- 31 August 2026; **core's Big_Pill: move `Tag_Areas.ts` into core, or make the component take what it needs as props.** The fault first: core's own check ran for the first time on 31 August 2026 and found that `Big_Pill.svelte` imports `Tag_Area`, `area_reads` and `tags_shown` from core's types barrel, which has never held them — they live in `ov/src/lib/ts/types/Tag_Areas.ts`. Five errors, one cause. The component has never compiled inside core, so the adoption plan's line saying ov should adopt it forward rests on a file that does not build. For moving the file: `Big_Pill` compiles at once, with no signature change and no edits at ov's two call sites. The three things it wants are honest library material — `Tag_Area` is a name and a list of words, and `tags_shown` and `area_reads` are pure: each takes an area and two lists and returns a list or a string, touching no store, no manager and nothing on screen. Against moving the file: the same file also holds `TAG_AREAS` — ov's ten named areas and its thirty-five tags — and `area_of` and `tags_without_area`, which read ov's closed tag list. That is the host's own vocabulary, and core's principle is that state lives in the host. A second host would inherit ov's words. Moving only the three means splitting one file in two, and two files named for one topic is the duplication bug. For the props: core stops naming the host's vocabulary at all. The component already takes `opened` and `ontoggle_area` as props for exactly this reason, so this is the treatment already chosen for this file, applied to the rest of it. What is handed in is two derived values the host already computes. Against the props: it is a signature change, so core's component and ov's two call sites change in one act, and every later host pays the same price. And a structural type still crosses the boundary — whatever `area` is, it has a name and a list of tags, so core knows that much of the host's data whether or not a type says so. The cost, counted: moving the file is one relocation and one barrel line. The props are a rewrite of the component's props block and edits at `Browse_Filters.svelte` line 348 and `Editor_Filters.svelte` line 523. Deciding question: is a pure function over a host's data library material, or does core stay clean only by knowing nothing about that data at all — not even the two functions that never touch a store? Decided 31 August 2026: keep core clean. Big_Pill takes what it needs as props; `Tag_Areas.ts` remains ov's.

- 30 August 2026; **only core has node modules — ov's moves there.** For: one copy of svelte, vite and typescript instead of a 16M pile per project; version skew between core and its hosts becomes impossible; core is what every host shares, so core holding the shared dependencies reads naturally; installs and disk both shrink. Against: node's resolver only walks *up* — ov cannot see a sibling's node_modules, so every tool (vite, tsc, vitest, the svelte plugin) would need aliases or symlinks, fighting the platform forever. And the wish already has a granted form: mono is a yarn workspace, whose whole job is hoisting shared dependencies to ONE pile at the root — 1,221 packages sit there now, and ov's own 16M exists only because of the deliberate `nohoist` for svelte. Moving the pile to core also inverts ownership: hosts would inherit core's lockfile choices even for host-only dependencies like markdown-it. A middle path: core declares the dependencies its code needs, ov depends on core, and the workspace hoists both to the root — "only core" becomes "only the root", which the machinery already supports; the open question is whether the svelte nohoist can go. Deciding question: is the wish one pile anywhere (the root already does it), or literally the pile living in core (which node's resolution fights everywhere)?
